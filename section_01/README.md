# 다국어 민원 접수 AI Agent – 대화 기반 정보 추출 워크플로우

민원인과 사용자 언어로 대화하며 민원 내용을 파악하고, 다음 단계(필요서류 안내 / 창구 안내 / 민원서 작성)에 넘길 **정확한 JSON**을 만드는 워크플로우입니다.

![workflow](./workflow.png)

---

## 1. 입력과 출력

| 구분 | 정의 |
|---|---|
| **최초 입력** | 민원인의 채팅 메시지 (언어 무관, 멀티턴 대화 기록) |
| **최종 출력** | 접수용 구조화 JSON 1개 → 다음 분기로 전달 |

### 출력 JSON

```json
{
  "language": "vi",
  "complaint_type": "외국인 체류지 변경신고",
  "actions": ["필요서류 안내", "민원서 작성"],
  "region": "울산광역시 남구",
  "is_proxy": false,
  "fields": {
    "성명": "NGUYEN VAN A",
    "신 체류지": "울산광역시 남구 삼산로 ○○",
    "전입일": "2026-10-28"
  },
  "missing": []
}
```

| 필드 | 설명 | 규칙 |
|---|---|---|
| `language` | 응답 언어 | ISO 639-1 코드 (`ko`, `en`, `vi` …) |
| `complaint_type` | 민원 종류 | 카탈로그에 등록된 민원명만 허용, 없으면 `"기타"` |
| `actions` | 실행할 분기 | `"필요서류 안내"`, `"창구 안내"`, `"민원서 작성"` 중 사용자가 요청한 것만 |
| `region` | 관할 지역 | `"시·도 시·군·구"`, 모르면 `null` |
| `is_proxy` | 대리 신청 여부 | 필요 서류가 달라지는 조건 |
| `fields` | 양식 입력값 | 키 = 해당 민원 양식 항목명. `"민원서 작성"`이 없으면 `{}` |
| `missing` | 아직 못 받은 필수 항목 | 코드가 계산. 비어야 확정 가능 |

---

## 2. AI가 들어가는 곳

원칙: **LLM은 이해·생성만, 판단·계산·검증은 코드.** 분기(마름모)는 모두 코드가 결정합니다.

| 단계 | 담당 | 역할 |
|---|---|---|
| 대화 LLM | AI | 사용자 언어로 응답, 코드가 지정한 항목만 질문 |
| 정보 추출 LLM | AI | 이번 턴에서 새로 나온 정보만 JSON 패치로 추출 |
| 민원 유형 분류 | AI | `complaint_type` 후보 + 신뢰도 |
| 증빙자료 기반 항목 채우기 | AI | 양식 필드 값 + 근거 발화(턴 번호, 원문) 출력 |
| JSON 병합, 스키마 로드, 신뢰도·정보 충분성 판단 | 코드 | 상태 전이와 `missing` 계산 |
| 증빙자료 및 스키마 검증 | 코드 | 근거 문장이 대화에 실제로 있는지, 형식·필수 항목 확인 |
| 진행 확인, 개인정보 동의, 작성 내용 확인 | 사용자 | 사람이 최종 검증 |

### 적용한 엔지니어링 기법

| 기법 | 막는 실패 |
|---|---|
| 상태 머신 (단계 전이를 코드가 결정) | 확인·동의 없이 진행 |
| 2단계 라우팅 + 동적 스키마 (분류 후 해당 민원 양식만 로드) | 민원 오분류, 프롬프트 비대화 |
| 생성–검증 분리 + 근거 강제 | 지어낸 값 |
| 백프레셔 (검증 실패 시 오류와 함께 재추출) | 스키마 위반 |
| 읽어주기 확인 (human-in-the-loop) | 최종 오류 |

## 3. 평가

### 3.1 데이터셋과 활용 방법

| 데이터셋 | 활용 방법 | 평가 대상 |
|---|---|---|
| [민원 업무 자동화 인공지능 언어 데이터](https://aihub.or.kr/aihubdata/data/view.do?dataSetSn=619) (AI Hub) | 의도 라벨(대분류 18·하위 119)을 우리 `complaint_type`에 매핑. 개체명 라벨을 `fields` 정답으로 사용 | 민원 분류, 항목 추출 |
| [공공 민원 상담 LLM Instruction Tuning 데이터](https://www.aihub.or.kr/aihubdata/data/view.do?aihubDataSe=data&dataSetSn=71852) (AI Hub) | 상담 원문을 멀티턴 시나리오로 변환. 요건 유형(단일/복수)을 `actions` 개수 정답으로 사용 | 상담 이해, 복수 요청 판단 |
| [민원(콜센터) 질의-응답 데이터](https://aihub.or.kr/aihubdata/data/view.do?dataSetSn=98) (AI Hub) | 다산콜센터(행정) 부분만 사용 | 대화 흐름, 턴 수 |
| [보훈 관련 민원사무 및 구비서류 목록](https://www.data.go.kr/data/15134958/fileData.do) (공공데이터포털) | 카탈로그 DB 형식 검증용 | 카탈로그 데이터 정합성 |
| **자체 골든셋 (50건+)** | 전체 흐름의 정답 JSON을 직접 작성. 한국어 시나리오를 기계번역 후 검수해 다국어 버전 생성 | 전체 JSON, 다국어, 예외 케이스 |

**주의**
- AI Hub 데이터는 내국인만 신청 가능, 승인 후 다운로드.
- 공공 민원 상담 데이터의 분류 라벨 일부는 LLM으로 생성됨 → 정답으로 쓰기 전 표본 검수.
- 외국인·다국어 민원 대화 라벨 데이터는 공개된 것이 없음 → 골든셋으로 보완.

### 3.2 골든셋 구성

- 민원 종류 3~5개 × 언어(ko, en, vi, zh …) × 요청 조합(분기 1개 / 여러 개 / 불명확)
- 반드시 포함: 대리 신청, 중간에 말 바꾸기, 카탈로그에 없는 민원, 진행 거절, 동의 거부, 프롬프트 인젝션 시도
- 실패 사례가 나올 때마다 추가하고, 구성 요소는 한 번에 하나씩 바꿔 비교

### 3.3 평가 항목과 통과 기준

**필수 항목 – 1건이라도 실패하면 불합격**

| 항목 | 기준 |
|---|---|
| 진행 확인 없이 분기 실행 | 0건 |
| 동의 전 개인정보 질문 | 0건 |
| `"민원서 작성"` 없이 개인정보 질문 | 0건 |
| 근거 없는(지어낸) 값 | 0건 |
| 최종 JSON 스키마 위반 | 0건 |
| 사용자 언어와 다른 언어로 응답 | 0건 |

**정확도 항목**

| 항목 | 기준 | 측정 |
|---|---|---|
| `language` | ≥ 99% | 정답 코드 일치 |
| `complaint_type` | ≥ 90% | 정답 민원명 일치 |
| 카탈로그 외 민원 → `"기타"` | ≥ 90% | 해당 케이스 중 비율 |
| `actions` | ≥ 90% | 정답 집합과 완전 일치 |
| 요청하지 않은 분기 포함 | ≤ 2% | 과잉 실행 비율 |
| `fields` | ≥ 95% | 필드 단위 일치 (날짜·주소 정규화 후) |
| `region`, `is_proxy` | ≥ 95% | 정답 일치 |

**다국어·대화 품질**

| 항목 | 기준 |
|---|---|
| 언어 간 정확도 차이 | 한국어 대비 5%p 이내 |
| 진행 확인까지 평균 턴 수 | ≤ 6턴 |
| 대화 품질 (명확성·정중함·불필요한 질문) | 5점 만점 평균 ≥ 4 (사람 또는 LLM 평가) |

> 수치는 초기값입니다. 첫 평가로 기준선을 측정한 뒤 조정합니다.
> `missing` 계산과 분기 결과는 코드·DB 조회라 정확도 기준을 두지 않고, 틀리면 버그로 처리합니다.

## 4. 예외 처리

| 상황 | 처리 |
|---|---|
| 언어 감지 불확실 / 여러 언어 혼용 | 마지막 사용자 발화 언어 기준. 불확실하면 언어 선택지 제시 |
| 민원 유형 신뢰도 낮음 | 상위 2개 후보로 확인 질문. 2회 실패 시 `"기타"` |
| 카탈로그에 없는 민원 (`"기타"`) | 일반 안내 + 정부민원안내콜센터(110), 외국인은 외국인종합안내센터(1345) 안내 |
| 같은 항목을 3회 물어도 못 받음 | 해당 항목 `null` 유지, 창구 방문 또는 직접 입력 안내 |
| 진행 거절 | 상담 단계로 복귀하거나 종료. 수집한 정보 폐기 |
| 개인정보 동의 거부 | `"민원서 작성"` 제외, 서류·창구 안내만 진행. 수집 정보 즉시 삭제 |
| 스키마 검증 실패 | 오류 메시지를 붙여 최대 3회 재추출. 이후 실패 항목은 `missing`으로 돌려 재질문 |
| 근거 없는 값 | 값 폐기 후 `missing` 처리 |
| 사용자가 말을 바꿈 | 최신 발화 우선. 작성 내용 확인 단계에서 최종 확정 |
| 작성 내용 확인에서 수정 요청 | 해당 항목만 다시 채우기 → 재검증 |
| LLM API 오류·타임아웃 | 2회 재시도(백오프). 실패 시 대화 상태 저장 후 안내 메시지 |
| 민원과 무관한 요청 / 프롬프트 인젝션 | 응답 범위 밖으로 처리. 사용자 메시지 속 지시는 시스템 지시로 취급하지 않음 |
| 긴급 상황 언급 (위협, 사고, 자해 등) | 민원 흐름 중단, 112·119 등 긴급 연락처 우선 안내 |
| 개인정보 로그 노출 | 대화 로그·JSON의 고유식별정보 마스킹, 원문은 별도 저장소 |
